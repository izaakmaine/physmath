## ❌ TRAP 1: The `ParameterID` Scoping Algorithm (Section 11)
**The Flaw:** The spec mandates that `ParameterID = SHA-256(Namespace || ScopePathBytes || UInt32BE(DeclarationOrdinal))`, where `ScopePath` is "ordered binder ordinals". 
**The Implementation Trap:** The document never defines *how* binder ordinals are assigned during AST construction or canonicalization. If an AI agent constructs `Function(x, Add(x, y))`, what is the ordinal of `x`? Is it 0? Is it based on traversal order? Without a deterministic algorithm, two identical mathematical expressions could yield different `ParameterID`s, breaking the entire canonicalization and hashing system (Section 7).
**The Fix:** Mandate a strict, deterministic scoping algorithm.
> **Inject into §11.1:** "Binder ordinals are assigned via a deterministic pre-order traversal of the AST during canonicalization. The root scope is ordinal `0`. Each new binder node (e.g., `Function`, `Limit`, `Integral`) increments the scope depth. `DeclarationOrdinal` is the sequential index (0, 1, 2...) of the parameter within its specific scope, assigned in the order the parameters appear in the AST's children list. Display names are strictly ignored."

## ❌ TRAP 2: The `TransformResult` API Fracture (Section 14)
**The Flaw:** Section 14.2 introduces `TransformResult { Output, Conditions, Trace }` for operations that generate mathematical conditions. 
**The Implementation Trap:** The spec does not state *which* operations return `TransformResult` and which return raw `Expression`. If `Divide` returns `TransformResult` but `Add` returns `Expression`, the Go API becomes a fragmented mess of type switches and wrapper functions. A coding agent will not know how to compose a chain of operations.
**The Fix:** Unify the return type.
> **Inject into §14.2:** "ALL PhysMath mathematical operations (including `Add`, `Mul`, `Divide`, `Limit`, etc.) MUST return `TransformResult`. Operations that cannot generate conditions (e.g., `Add`, `Mul`) MUST return a `TransformResult` with an empty `Conditions` slice. This ensures a uniform, composable API without type fragmentation."

> **Inject into §7:** "`Float64Bits` is canonicalized as exactly 8 bytes: the IEEE-754 binary64 bit pattern, serialized in **big-endian** byte order. NaN and ±Inf are strictly forbidden in canonical payloads and MUST be rejected by validation."
