The architecture specification v1.4 contains 5 valid architectural blockers under §34.2 that require resolution before the specification can be frozen for implementation.

## 1. Demonstrated Architectural Blockers

### Blocker 1: Field Order Inconsistency Between `EmbeddedArtifactRef` (§6.3) and `SET` Sorting Key (§6.4)

* **Location:** §6.3, §6.4
* **Blocker Criteria:** §34.2(1) — Contradiction between normative rules.
* **Concrete Counterexample:**
* §6.3 defines the normative byte framing order for `EmbeddedArtifactRef` as:

$$\text{Namespace} \mathbin{\Vert} \text{SchemaVersion} \mathbin{\Vert} \text{ArtifactType} \mathbin{\Vert} \text{Digest}[32]$$


* §6.4 defines the lexicographic sorting key order for `ArtifactRef` `SET` collections as:

$$\text{Namespace} \mathbin{\Vert} \text{ArtifactType} \mathbin{\Vert} \text{SchemaVersion} \mathbin{\Vert} \text{Digest}[32]$$


* Consider two references:
* $\text{Ref}_A = \{\text{Namespace: } \text{"ns"}, \text{SchemaVersion: } \text{"1"}, \text{ArtifactType: } \text{"z\_type"}, \text{Digest: } [0x01\dots]\}$
* $\text{Ref}_B = \{\text{Namespace: } \text{"ns"}, \text{SchemaVersion: } \text{"2"}, \text{ArtifactType: } \text{"a\_type"}, \text{Digest: } [0x01\dots]\}$


* Under §6.3 serialized byte comparison ($\text{SchemaVersion}$ before $\text{ArtifactType}$), $\text{Ref}_A$ ("1") comes **before** $\text{Ref}_B$ ("2").
* Under §6.4 struct field comparison ($\text{ArtifactType}$ before $\text{SchemaVersion}$), $\text{Ref}_B$ ("a_type") comes **before** $\text{Ref}_A$ ("z_type").


* **Failure Consequence:** Two implementations sorting a `SET` of `ArtifactRef`s will construct different byte arrays and compute different SHA-256 digests depending on whether they sort by serialized `EmbeddedArtifactRef` bytes or by §6.4 tuple order.
* **Required Remediation:** Re-align §6.4 field ordering to match §6.3 (`Namespace`, `SchemaVersion`, `ArtifactType`, `Digest[32]`) or explicitly mandate that `SET` sorting MUST perform raw lexicographic byte comparison over the §6.3 canonical byte encoding of `EmbeddedArtifactRef`.

### Blocker 2: Complete Absence of `CanonicalParameters` Schemas for RuleIDs (§10.11, Appendix B.1)

* **Location:** §10.11, Appendix B.1
* **Blocker Criteria:** §34.2(4) — Implementation agent must invent architecture.
* **Concrete Counterexample:**
* §10.11 defines the `Transformation` artifact with field `Parameters CanonicalParameters`, stating: *"Its schema, field order, and valid values are defined by the exact RuleID. A transformation MUST reject parameters that are not valid for its RuleID; there is no open-ended parameter bag."*
* Appendix B.1 lists 55 concrete `RuleID`s (`ID-001`, `EXPR-001` through `EXPR-005`, `FN-001`… `PROJ-001`), but v1.4 specifies **zero** parameter schemas, binary encodings, or validation rules for any of these 55 `RuleID`s.


* **Failure Consequence:** An implementation agent constructing or validating a `Transformation` artifact (e.g. for `TR-001` or `EXPR-001`) cannot determine the binary format or valid range for `CanonicalParameters` without inventing schemas for all 55 `RuleID`s.
* **Required Remediation:** Define explicit canonical schemas (or explicitly specify an empty byte sequence `[]byte{}` where no parameters are required) for `CanonicalParameters` across all 55 `RuleID` entries in Appendix B.1.

### Blocker 3: Missing Parameter Fields in `Operator` / `OperatorApplication` for Differential Operators (§10.5, §10.6, §12.1)

* **Location:** §10.5, §10.6, §12.1
* **Blocker Criteria:** §34.2(3) — Required schema field is absent.
* **Concrete Counterexample:**
* §12.1 mandates: *"A differential operator is represented as an `OperatorApplication` whose canonical operator identity is `differentiate` and whose canonical parameters contain: Target ParameterID [and] Order UInt32."*
* However, the schema definitions in §10.5 and §10.6 are:
```text
Operator {
    OperatorID string
    Domain     MathTypeRef
    Codomain   MathTypeRef
    Definition ArtifactRef
}

OperatorApplication {
    OperatorRef ArtifactRef
    Args        []ArtifactRef
}

```


* Neither `Operator` nor `OperatorApplication` possesses a parameter payload field to hold `Target ParameterID` ($32\text{ bytes}$) and `Order UInt32` ($4\text{ bytes}$). `Args` is restricted to `[]ArtifactRef`, which cannot embed primitive scalars without violating §6.3.


* **Failure Consequence:** Coding agents cannot construct or parse a differential operator (`differentiate`) because there is no schema field in `Operator` or `OperatorApplication` to store differentiation parameters.
* **Required Remediation:** Update `OperatorApplication` or `Operator` in §10.5/§10.6 to include a parameter payload field (e.g., `Parameters []byte` or explicit `Target ParameterID` and `Order uint32` fields).

### Blocker 4: Unspecified Collection Semantics for `ComputationalContract.ProvenanceRefs` (§6.4, §7.2, Appendix A.15)

* **Location:** §6.4, §7.2, Appendix A.15
* **Blocker Criteria:** §34.2(2) — Two legitimate implementation choices remain.
* **Concrete Counterexample:**
* §6.4 dictates: *"Every canonical collection MUST explicitly declare `SET` or `SEQUENCE` semantics in its owning schema or in the complete collection table in §7.4 [referring to §7.2]."*
* §7.2 explicitly classifies `ComputationalContract.Inputs`, `ComputationalContract.Parameters`, and `ComputationalContract.RequestedOutputs` as `SET`s.
* However, `ComputationalContract.ProvenanceRefs` (`[]ArtifactRef`) is omitted from both the `SET` and `SEQUENCE` tables in §7.2 and from Appendix A.15.


* **Failure Consequence:** One implementation agent will preserve the declared slice order (`SEQUENCE`), while another will sort entries lexicographically (`SET`), producing divergent canonical digests for identical contracts.
* **Required Remediation:** Add `ComputationalContract.ProvenanceRefs` explicitly to either the `SET` or `SEQUENCE` table in §7.2.

---

### Blocker 5: Unresolvable Cross-Artifact Parameter Context Retention Mandate (§9.3, §11.1, §11.4, Appendix A)

* **Location:** §9.3, §11.1, §11.4, Appendix A
* **Blocker Criteria:** §34.2(3) — Required schema/identity binding is absent.
* **Concrete Counterexample:**
* §11.1 establishes: *"In v1, the only schema-defined binder is `Function.ParameterIDs`."*
* §11.4 mandates: *"When a parameter is intentionally shared across artifacts, the durable research or composition artifact MUST retain the declaring artifact `ArtifactRef` separately from the `ParameterID`."*
* However, standalone `physmath/expression/1` artifacts (§9.3 `Symbol` only stores `Optional(ParameterID)`), `Transformation`, `MathTrace`, and `ResearchStep` schemas provide no field to store `DeclaringArtifactRef`.


* **Failure Consequence:** Coding agents cannot satisfy §11.4 when reusing parameters across artifacts because no published schema in Appendix A provides a field to store the `(DeclaringArtifactRef, ParameterID)` binding.
* **Required Remediation:** Introduce a canonical bound-parameter tuple (e.g., `BoundParameterRef { DeclaringArtifactRef ArtifactRef, ParameterID ParameterID }`) and incorporate it into the relevant schemas where cross-artifact parameter references occur.
