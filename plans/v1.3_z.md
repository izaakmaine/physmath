## 2. 🔴 Blocker — `ParameterID` derivation is not injective; v1.3 fails its own mandatory t/k test

**§11.1** derives `ParameterID = SHA-256(String(Namespace) ‖ ScopePathBytes ‖ UInt32BE(DeclarationOrdinal))` where `ScopePath` runs "from the artifact root to the declaration scope." Concrete collision: artifact **A** declares `t` as its first root-level parameter; artifact **B** independently declares `k` as its first root-level parameter. Both are in namespace `physmath`, both have empty `ScopePath`, both have ordinal `0` — **identical `ParameterID`.** Under §12.1, `∂/∂t` and `∂/∂k` then target the same operator parameter — the two flows are mathematically identical, and the mandatory invariance test (§12.2–12.4) fails for precisely the most common case: two independently created artifacts.

The derivation needs one more input that distinguishes declarations: **the declaring artifact's identity**. Fix (one paragraph): `ParameterID = SHA-256(String(Namespace) ‖ Embed(DeclaringArtifactRef) ‖ ScopePathBytes ‖ UInt32BE(DeclarationOrdinal))` — cross-artifact reuse then works exactly as §11.4 already contemplates ("referenced by its declaration artifact or stable ParameterID": the ID is derived once, at declaration, and referenced thereafter; independent declarations are distinct; shared declarations are shared). Everything else in §11 (alpha-renaming invariance, no-UUID rule, display-name exclusion) survives unchanged. Without this fix, §12's central guarantee is false for independently authored artifacts — the normal case for an AI-agent ecosystem.

## 3. Must-pin schema ambiguities (each resolvable in one sentence; all are places an agent must currently choose)

1. **`Pow.Exponent` type is unstated (§9.7).** "Broader than the frozen Phys projection domain" + reason code `NON_RATIONAL_EXPONENT_IN_POW` (§20.5/§20.7) only make sense if `Exponent` is an **Expression** (symbolic exponents representable, Rational-literal the projectable case). Pin the field type — as written, an agent could implement `Exponent : Rational`, making the reason code unreachable and §9.7 false.
2. **`Call.FunctionRef` type is unstated (§9.9).** §10.2 uses `FunctionRef ArtifactRef`; pin Call's identically.
3. **`Operator.OperatorID` and `Transformation.RuleID` are bare strings (§10.5, §10.11) with no scope.** Two packages defining an operator named `differentiate` collide — and §12.1's canonical operator identity is exactly such a bare string. Pin: IDs are namespace-qualified (`physmath.differentiate`) or ArtifactRefs; the PhysMath-owned vocabularies (operator IDs, rule IDs) are enumerated in the implementation spec under a no-collision rule. This is load-bearing for the t/k law.
4. **`Relation` is both an Expression node kind (§9.10) and a top-level sort (§9 list, §7.1 `relation`).** The relationship is unstated: is a `relation` artifact an Expression whose root kind is Relation (alias), or a distinct payload? (Note `BranchSet` has the node kind but *no* sort — the asymmetry suggests alias.) Pin it; also note the operator-string drift (`NE` vs frozen Phys `neq`) — harmless while relations are non-projectable, but state that a future relation bridge must adopt the frozen vocabulary exactly.
5. **Projection of bound symbols (§20.3 vs §9.3).** A PhysMath `Symbol` carries `ParameterID`/`ConstantID`; frozen Phys symbols are display-name-only. Strictly read, projection drops binding identity → "required information lost" → every symbolic expression is `UNREPRESENTABLE` under zero-permitted-loss. The evident intent is that Phys's name-only symbol semantics *is* the target semantics, so binding metadata not representable *and not required by the target model* is not loss. Pin that sentence — its absence makes the strict reading absurd and the loose reading unpinned. Same for `ConstantID` → symbol name.
6. **Canonicalization handoff on projection (§9.6 vs frozen Phys).** PhysMath MAY retain `Neg(Neg(x))` pre-normalization; frozen Phys removes it at construction. One sentence: the projected artifact is the Phys-canonical form (Phys constructor canonicalization applies on arrival); projection is not required to be injective.
7. **`PROJECTABLE` outcome usage (§19.3).** The only MVP success terminal is `(RESOLVED, PROJECTED_AS_HYPOTHESIS)`; when does `Outcome = PROJECTABLE` occur — review-positive-but-not-projected? Pin or drop from the MVP outcome set.
8. **`InterpretationClass string` (§16.4) has no stated vocabulary.** Prior rounds pinned the closed two-value rule (`INTERPRETATION_NEUTRAL` / `FRAMEWORK_SPECIFIC`). If it lives in the truncated conformance section, cross-reference it; otherwise pin it here.
9. Small: `Tensor.IndexRefs[i]` ↔ mode-*i* correspondence (one line); §12.1's canonical form for repeated differentiation (pin single-application with `Order = n`, or the repeated form — one of the two); `LimitDirection`/`Variance`/`FailurePolicy` (§15) are correctly PhysMath-owned and non-redefinable ✓.
