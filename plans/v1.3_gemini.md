### Identified Architectural Blockers

#### BLOCKER 1: Unspecified Binary Serialization for `physmath.expression` AST

* **Sections:** §9.2–§9.11, §28.1, Appendix A.1
* **Defect:** Missing schema layout for core mathematical payload. Appendix A.1 states that `ExpressionArtifactPayload.PayloadBytes` is *"the recursive tagged union defined in §9.2–§9.11"*. However, §9.2–§9.11 provides **no binary wire layout**, no tag byte discriminators for the 10 node kinds (`Symbol`, `Rational`, `Add`, `Mul`, `Neg`, `Pow`, `Sqrt`, `Call`, `Relation`, `BranchSet`), no field ordering for AST nodes, and no binary encoding for `Symbol` constants or comparison operators (`EQ`, `NE`, `LT`, etc.).
* **Concrete Counterexample:**
* Agent A encodes node tags as 1-byte unsigned integers (`Symbol=0x01`, `Rational=0x02`, `Add=0x03`...).
* Agent B encodes node tags as length-prefixed UTF-8 strings (`"Symbol"`, `"Rational"`, `"Add"`...).


* **Failure Consequence:** Both agents generate syntactically valid byte streams, but their `CanonicalPayloadBytes` and SHA-256 `ArtifactRef` digests are completely incompatible. A coding agent must invent the entire AST serialization protocol.

#### BLOCKER 2: Contradiction in `ArtifactRef` Field Order (Struct Declaration vs. Framing Sequence)

* **Sections:** §5.1, §6.2, §6.3, §7
* **Defect:** Direct rule contradiction. Section 5.1 defines the Go struct field order as:
```go
type ArtifactRef struct {
    Namespace     string
    ArtifactType  string
    SchemaVersion string
    Digest        [32]byte
}

```


Section 7 mandates: *"Canonical struct fields appear in the exact declaration order specified by the artifact schema."*
However, §6.2 and §6.3 explicitly specify framing as:

$$\text{Len32}(\text{Namespace}) \mid\mid \text{UTF8}(\text{Namespace}) \mid\mid \text{Len32}(\text{SchemaVersion}) \mid\mid \text{UTF8}(\text{SchemaVersion}) \mid\mid \text{Len32}(\text{ArtifactType}) \mid\mid \text{UTF8}(\text{ArtifactType}) \mid\mid \dots$$



swapping `ArtifactType` and `SchemaVersion`. Furthermore, §7 requires SETs of `ArtifactRef` to be sorted by `(Namespace, ArtifactType, SchemaVersion, Digest)`.
* **Concrete Counterexample:**
* Agent A follows §7 (declaration order from §5.1): `Namespace` $\rightarrow$ `ArtifactType` $\rightarrow$ `SchemaVersion` $\rightarrow$ `Digest`.
* Agent B follows §6.2/§6.3 framing order: `Namespace` $\rightarrow$ `SchemaVersion` $\rightarrow$ `ArtifactType` $\rightarrow$ `Digest`.


* **Failure Consequence:** Canonical payload digests for any struct containing an embedded `ArtifactRef` diverge across implementations.

#### BLOCKER 3: Contradictory Framing Specification for `ParameterID` Calculation

* **Sections:** §7, §11.1
* **Defect:** Direct rule contradiction in parameter identity framing. Section 11.1 defines the canonical byte sequence for a parameter as:

$$\text{String}(\text{Namespace}) \mid\mid \text{Bytes}(\text{ScopePathBytes}) \mid\mid \text{UInt32BE}(\text{DeclarationOrdinal})$$



where sentence 1 defines `ScopePathBytes` as `UInt32BE(len(ScopePath)) || UInt32BE(ScopePath[0]) ...`, and sentence 3 states: *"ScopePathBytes therefore uses fixed-width 32-bit elements; its length prefix is the number of elements, not the number of encoded bytes."*
However, §7 explicitly defines `Bytes(b) = Len32(len(b)) || b`, where `len(b)` is the total byte length ($4 \times \text{len}(\text{ScopePath})$).
* **Concrete Counterexample:**
* Agent A applies `Bytes(ScopePathBytes)` per §7: prefixes `ScopePathBytes` with its total byte length `Len32(4 * len(ScopePath))`, resulting in two length prefixes (byte length, then element count).
* Agent B obeys sentence 3 of §11.1: emits `ScopePathBytes` without wrapping it in §7's `Bytes()`, yielding a single length prefix of element count.


* **Failure Consequence:** Identical mathematical parameter declarations generate completely different `ParameterID` digests across implementations.

#### BLOCKER 5: Unspecified Binary Encoding for Schema Enum Types

* **Sections:** §7, §10.12, §10.14, §18.2, §19.2, §26
* **Defect:** Missing primitive encoding rule for enums. The specification uses multiple enum types across schemas: `ResearchState` (§18.2), `FormalizationOutcome`/`ProposalOutcome` (§19.2/§19.3), `ProjectionClass` (§19.2/§20.2), `LimitDirection` (§10.12), `Variance` (§10.8), and `FailurePolicy` (§10.14). Section 7 defines primitive encodings (`String`, `Bytes`, `UInt8`, `UInt32`, `Bool`, `Array`, `Optional`, `Digest32`), but fails to specify whether enum values are serialized as `String(enum_label)` (e.g., `Len32(8) || "PROPOSED"`) or as byte/integer ordinals (`UInt8`).
* **Concrete Counterexample:**
* Agent A serializes `ResearchState.PROPOSED` as `String("PROPOSED")` (12 bytes: `0x00000008` + `"PROPOSED"`).
* Agent B serializes `ResearchState.PROPOSED` as `UInt8(0)` (1 byte: `0x00`).


* **Failure Consequence:** Canonical payload digests diverge for every artifact containing an enum field.

#### BLOCKER 7: Missing Variant Tag Discriminator for `NumericScalar`

* **Sections:** §24.3, Appendix A.15
* **Defect:** Binary ambiguity in schema parsing. Appendix A.15 defines `NumericScalar = Rational | Float64Bits`. `Rational` (§9.4 + §7) is serialized as sign byte + length + magnitude bytes for numerator and denominator. `Float64Bits` is serialized as an 8-byte `UInt64BE` IEEE-754 bit pattern. When serializing `NumericScalar` fields inside `InputBinding` or `NumericParameter`, the specification provides no discriminator tag byte (`UInt8`) to identify which variant is present.
* **Concrete Counterexample:**
* Agent A prepends a 1-byte type tag (`0x01` for `Rational`, `0x02` for `Float64Bits`).
* Agent B emits raw payload bytes without a tag byte, causing decoding failures when a `Rational` payload coincidentally occupies 8 bytes.


* **Failure Consequence:** Binary decoding of `ComputationalContract` numeric arrays is non-deterministic without inventing unstandardized tag bytes.
