## Adversarial Review — `PHYSMATH_PHYS_EXTERNAL_ARCHITECTURE_v1.4.md`

**Context reviewed:** v1.4 against §34.2’s own blocker test — “Can a competent coding agent, given only v1.4 and the frozen Phys authority identified in §0.1, still choose between two architecturally legitimate implementations?”

**Verdict:**  
**NOT CLOSED. NINE DEMONSTRATED BLOCKERS REMAIN.**  
v1.4 resolves all eight blockers from the v1.3 review. It also closes the sort-count, Relation dual-role, ParameterID namespace, RequestedTarget, condition artifact, outcome→state, and constant-resolution issues. The document is materially stronger.

However, nine further blockers satisfy §34.2’s definition: two legitimate implementations remain, or a required rule/schema/vocabulary is absent, or the coding agent must invent architecture. The most consequential are the undefined RuleID semantics (used as the closed vocabulary for Transformation.RuleID), the undefined ConstantID type, the undefined canonical `differentiate` Operator, and the undefined `ProjectionClass` value when no projection occurs.

## II. Demonstrated architectural blockers

Each blocker identifies the section, a concrete counterexample, and the failure consequence, per §34.2.

### Blocker 1 — RuleID semantics are undefined while RuleID is a required serialized value

- §10.11: `Transformation.RuleID` MUST be "a closed exact identifier from the concrete v1 RuleID registry in Appendix B."
- Appendix B.1 lists 56 IDs (`EXPR-001`, `EXPR-002`, …, `PROJ-001`), all marked “concrete serialized identifiers.”
- Appendix C uses these IDs as contract-matrix cells (Construct / Canonicalize / Equality / Substitute for each sort).
- No appendix section defines what any RuleID *does*.
- §10.11 also says “`CanonicalParameters` is a byte string produced by the named transformation rule. Its schema, field order, and valid values are defined by the exact RuleID.” No RuleID specifies a parameter schema.
- §23.1 states `MathTrace.ParameterBytes` similarly “produced by the named transformation rule.”

**Counterexample:** A coding agent must implement `Transformation{Inputs, Output, RuleID:"EXPR-002", Parameters:…}`. What is the byte encoding of `Parameters` for `EXPR-002`? Which expression transformation does `EXPR-002` produce, and how is its input interpreted? `EXPR-002` is described as “canonicalization” in Appendix C; §9.5 gives flattening/sorting for `Add`/`Mul`; §9.6 gives a double-negation rule `EXPR-005`. But there is no rule `EXPR-002` producing a single deterministic output for arbitrary Expression inputs.

Two implementations are legitimate: one treats `EXPR-002` as the union of §9.5 and §9.6 canonicalization; another treats `EXPR-002` as a caller-selected subset requiring additional context. They produce different Transformation artifacts for the same intent.

**Failure consequence:** `MathTrace` replay is impossible for any transformation whose RuleID is not exhaustively specified; A→B and A→B' produce different content-addressed artifacts for identical mathematical intent; cross-project interchange of transformation traces fails.

**Exit condition:** For each RuleID in Appendix B, provide (a) the exact operation semantics as a function from inputs to output, (b) the exact byte schema of its `CanonicalParameters`/`ParameterBytes`, and (c) the closed vocabulary of any sub-parameters.

### Blocker 2 — `ConstantID` is referenced but never defined

- §9.3: `Symbol` has `ConstantID?` — “optional mathematical constant identifier.”
- §13.1 gives string examples: `math.const.pi`, `math.const.e`.
- No section defines `ConstantID`'s Go type, encoding, canonical form, or scope.
- §9.2’s Symbol encoding declares `Optional(ConstantID)` without saying what the payload bytes are.

**Counterexample:** Two coding agents must encode `Symbol{ConstantID: pi}`. One chooses `ConstantID = string`, encoding `String("math.const.pi")`; another chooses `ConstantID = [32]byte` derived from the constant name, encoding `Digest32(...)`. Both satisfy every other rule in v1.4, produce different canonical bytes for the same symbolic content, and different `ArtifactRef`s.

**Failure consequence:** `Symbol` identity and equality are implementation-dependent; Phys projection of π-symbols is not portable.

**Exit condition:** declare `ConstantID` as a concrete Go type with exact canonical encoding; declare the namespace and canonical registry for mathematical constants; or fold `ConstantID` into `ParameterID` with an explicit mathematical-constant classification.

---

### Blocker 3 — The canonical `differentiate` Operator is not specified

- §12.1: differential operators are `OperatorApplication`s whose "canonical operator identity is `differentiate`."
- §10.6: `OperatorApplication{OperatorRef ArtifactRef, Args []ArtifactRef}`.
- §10.5: `Operator{OperatorID, Domain, Codomain, Definition}`.
- Appendix B.2: the closed OperatorID vocabulary is exactly `differentiate`.
- No section defines:
  - the `ArtifactRef` of the canonical `differentiate` Operator;
  - its `Domain`/`Codomain`/`Definition` fields;
  - its canonical byte representation;
  - how two implementations agree on the same `ArtifactRef` for `differentiate`.

**Counterexample:** Coding agent A defines the `differentiate` Operator with `Definition` empty and `Domain`/`Codomain` as `expression`/`expression`. Coding agent B defines it with `Definition` = a specific reference to §12 and `Domain`/`Codomain` = `function`/`function`. Their `ArtifactRef`s for the canonical operator differ; every `OperatorApplication` referencing `differentiate` differs across implementations; two `MathTrace`s of the same differentiation operation do not match.

**Failure consequence:** The t/k invariance law (§12) is unenforceable because the identity of the differentiating operator itself is implementation-dependent.

**Exit condition:** specify the canonical `differentiate` Operator as a fixture with a fixed canonical byte representation and expected `ArtifactRef`, or make `differentiate` a reserved tag that does not require an Operator artifact.

### Blocker 4 — `OperationSchemaVersion` semantics are undefined

- §23.1: `MathTrace.OperationSchemaVersion string`.
- No section defines what this string identifies.
- Candidates include: PhysMath schema version (would be `"1"`), the RuleID’s own version, a per-operation schema version, or a container-schema version.

**Counterexample:** Two coding agents implement `MathTrace` for the same operation. One sets `OperationSchemaVersion = "1"` (PhysMath version); the other sets it to `"2024-11"` (per-rule version). Both pass every rule in v1.4. Their canonical bytes and `ArtifactRef`s differ.

**Failure consequence:** Traces produced by one implementation cannot be validated or replayed by another.

**Exit condition:** declare the exact source of `OperationSchemaVersion` and its value set for v1.

---

### Blocker 5 — §13.3 and §24.3 contradict each other on constant resolution

- §13.3: "Numerical lowering MAY resolve exact mathematical or physical constants to numerical values only when the owning mathematical/physical contract supplies an explicit deterministic mapping."
- §24.3: "Numerical MUST NOT infer, look up, reinterpret, or recompute symbolic constants. A producing phys-* package or other contract owner MUST deterministically resolve any required exact mathematical or physical constant before constructing the numerical contract."

If “numerical lowering” in §13.3 is the same phase as “Numerical” in §24.3, the two rules contradict. If they are different phases, that is not stated.

**Counterexample:** A coding agent implementing the boundary must decide whether a producing `phys-*` package is required to materialize constants before constructing `ComputationalContract` (§24.3) or whether Numerical may legitimately resolve them (§13.3). Both readings are compatible with the text as written.

**Failure consequence:** Implementations disagree about where the constant→numeric step lives; Numerical receives contracts with different expectations of completeness.

**Exit condition:** rename or disambiguate “numerical lowering” from “Numerical”; state whether the resolution phase is upstream of `ComputationalContract` construction or part of the producer’s responsibility.

### Blocker 6 — `FormalizationResponse.ProjectionClass` is required for outcomes where no projection occurs

- §A.13: `FormalizationResponse.ProjectionClass ProjectionClass` is a required field.
- §19.5: outcomes include `REQUEST_REVISION` and `REJECTED`, in which no projection occurs.
- §20.2: `ProjectionClass` is `FULLY_REPRESENTABLE | PARTIALLY_REPRESENTABLE | UNREPRESENTABLE`.
- No section states which value to use when the outcome is not a projection result.

**Counterexample:** A coding agent must produce a `FormalizationResponse` with `Outcome = REJECTED`. Should `ProjectionClass` be `UNREPRESENTABLE` (implying the source can never be represented), or is there an unlisted fourth value? Two implementations choose differently; responses for the same rejected proposal have different canonical bytes.

**Failure consequence:** Responses are non-portable across implementations; rejection reasons become ambiguous.

**Exit condition:** either declare `ProjectionClass` optional and specify when it is present, or add an explicit `NOT_ATTEMPTED` value, or specify the exact value for each outcome.

---

### Blocker 7 — `InterpretationClass` value set is not enumerated

- §16.1: `PhysicalInterpretation.InterpretationClass string`.
- §16.4: `PhysicalContract.InterpretationClass string`.
- No section lists valid values.
- Prior architecture chain (v1.3 and earlier) specified `INTERPRETATION_NEUTRAL` and `FRAMEWORK_SPECIFIC`; v1.4 does not carry those forward.

**Counterexample:** A coding agent must populate `InterpretationClass` for a new `phys-qm` interpretation. Without a closed vocabulary, one implementation uses `"neutral"` and another uses `"INTERPRETATION_NEUTRAL"`. Both satisfy the letter of v1.4.

**Failure consequence:** Downstream consumers cannot filter by interpretation class; conformance checks around interpretation ambiguity (§17) cannot be enforced.

**Exit condition:** enumerate the closed value set and declare it as a typed enum with a canonical string encoding.

---

### Blocker 8 — `FrameworkRef` target artifact type is undefined

- §16.1: `PhysicalInterpretation.FrameworkRef ArtifactRef`.
- §16.4: `PhysicalContract.FrameworkRef ArtifactRef`.
- No section specifies what kind of artifact `FrameworkRef` points to, what namespace it lives in, what its `ArtifactType` is, or how it is produced.

**Counterexample:** A coding agent must produce a `PhysicalInterpretation` with a `FrameworkRef`. Options include pointing at (a) a `<framework>/contract/1` artifact, (b) a `<framework>/interpretation/1` artifact, (c) a new package-metadata artifact family, or (d) a string identifier promoted to `ArtifactRef`. Each is consistent with the text; the canonical `ArtifactRef` differs across implementations.

**Failure consequence:** Framework identity is not portable; two implementations cannot resolve each other’s framework references.

**Exit condition:** declare the exact artifact family for framework identity, its namespace, and its schema; or replace `FrameworkRef` with a namespace string.

---

### Blocker 9 — `ProjectionLossReport.ProjectionReason.NodeKind` vocabulary is not closed

- §20.7: `ProjectionReason{Code, NodeKind, Detail}`.
- `Code` has an explicit closed vocabulary (§20.7).
- `NodeKind` is a `string` with no enumerated values.

**Counterexample:** A coding agent must record `NodeKind` for a projection failure. One uses `"Pow"` (matching §9.2’s NodeKind labels); another uses `"pow"` or `"0x06"` (matching the tag). Canonical `ProjectionLossReport` bytes differ.

**Failure consequence:** Loss reports are non-portable; condition finalization ordering in §14.4 depends on the digest of these reasons, which depends on `NodeKind` encoding.

**Exit condition:** enumerate the `NodeKind` vocabulary or bind it explicitly to §9.2’s tag values via a fixed mapping.

## III. Minor but real issues

- **§6.4 cross-reference:** It says "in its owning schema or in the complete collection table in §7.4." §7.4 is the artifact-type mapping table; the collection table is §7.2. This is a citation error but could mislead a coding agent looking for the collection table.
- **§10.11 `CanonicalParameters`:** "a byte string produced by the named transformation rule" — same family of problem as Blocker 1; subsumed once RuleID semantics are pinned.
- **§16.1 `ConventionRequirement`:** No canonicalization rule against a `Phys` convention vocabulary; acceptable if declared out-of-scope, but the doc doesn’t say that.
- **§18.1 `CorrespondenceProposal.ProposalVersion`:** semantics of version numbering are not specified (monotonic? per correspondence chain?).
- **§19.1 `FormalizationProposal.ProposalRevision`:** initial value (`0` or `1`?) not specified.
- **§20.7 `ProjectionLossReport.Reasons` ordering:** “Reasons are sorted by `(Code, NodeKind, Detail)`” — but `NodeKind`'s encoding is undefined (Blocker 9), so the sort is undefined.
- **§24.3 `PrecisionRequirement` / `ExecutionLimits`:** all-optional structs; is “all absent” legal? Not stated.
- **§25.4 placement:** It states an inherited frozen-Phys check inside the `phys-*` conformance contract; the text does note it is not universal, but placement remains confusing.
- **§25.8 `ops`:** The doc says `ops` must not branch on physical names — but `ops` is a Phys-internal package name from the frozen spec. If the check applies to PhysMath’s operation layer, "ops" is the wrong word; if it applies to Phys, then it belongs in the frozen Phys authority, not in this document.
- **§25.10:** Similar — “mechanics/relativity established-constructor allowlists” are frozen Phys facts, listed as a `phys-*` conformance rule.
- **§B.1:** Lists 56 RuleIDs but Appendix C uses `RULE EXPR-001` in a way that suggests these are the sort-matrix cells, while §10.11 uses them as `Transformation.RuleID` values. The document does not distinguish “matrix rule reference” from “serialized transformation RuleID.” This is a structural confusion underlying Blocker 1.
- **§A.10:** `PreviousStateRef` points to a FormalizationProposal artifact of the same revision; combined with §19.2's rule that `ProposalRef` must point to the RESOLVED artifact, the graph is well-defined but the first-DRAFT’s `nil` `PreviousStateRef` is a value that must be validly encoded as `Optional(nil)` — consistent with §7, so fine, but worth noting in a golden vector.
- **Appendix C:** The “Project” column marks most sorts as `UNREPRESENTABLE`; this is a statement about the MVP projection contract, not about the sort. A coding agent must not interpret this as “these sorts cannot exist.”

## V. Path to closure

To satisfy §34.5, v1.4 must resolve the nine blockers above. Concretely:

1. **Blocker 1.** For each RuleID, provide exact operational semantics and canonical parameter bytes; or reduce the RuleID registry to those rules whose semantics are fully specified and mark the rest as documentation-only references not valid as `Transformation.RuleID`.
2. **Blocker 2.** Pin `ConstantID` as a concrete type with a canonical encoding and a reserved namespace.
3. **Blocker 3.** Pin the canonical `differentiate` Operator as a fixture with a fixed ArtifactRef, or promote `differentiate` to a tagged variant of `OperatorApplication` that does not require an Operator artifact.
4. **Blocker 4.** Declare what `OperationSchemaVersion` identifies and its valid values.
5. **Blocker 5.** Disambiguate §13.3 from §24.3; state whether constant resolution occurs upstream of the `ComputationalContract` or is forbidden in Numerical.
6. **Blocker 6.** Specify `ProjectionClass` for non-projection outcomes, or make the field optional, or add a `NOT_ATTEMPTED` value.
7. **Blocker 7.** Enumerate `InterpretationClass` values and their canonical string encoding.
8. **Blocker 8.** Declare the artifact family for `FrameworkRef` or replace it with a typed identifier.
9. **Blocker 9.** Close `NodeKind` to the ten tag names from §9.2 or to the corresponding sort names with an explicit mapping.

Then apply the minor clarifications. After that, the No-Invention Matrix should add rows for `ConstantID`, the canonical `differentiate` operator, `InterpretationClass`, `FrameworkRef`, `NodeKind`, and the RuleID semantics source, so §32’s closure rule actually holds.
