## Adversarial Review — `PHYSMATH_PHYS_EXTERNAL_ARCHITECTURE_v1.3.md`

**Context reviewed:** v1.3 against the target stated in its own §34.2 — “Can a competent coding agent, given only v1.3 and the frozen Phys authority identified in §0.1, still choose between two architecturally legitimate implementations?”

**Verdict:**  
**NOT CLOSED.** v1.3 is the strongest document in the series. It correctly pins identity, framing, canonical encoding, sort families, parameter identity, projection, formalization protocol, and the No-Invention Matrix. But **eight demonstrated blockers remain**, each satisfying §34.2’s own definition of a valid blocker (two legitimate implementations remain; required schema/owner/state is absent; the coding agent must invent architecture).

The most consequential are: the sort count is internally inconsistent; the operator/rule vocabulary is not enumerated; the `Relation` sort has two incompatible homes; the `RequestedTarget` string conflicts with the referenceable Phys artifact type; and the formalization outcome → hypothesis state mapping is not defined.

---

## I. What v1.3 gets right

These are load-bearing and should be preserved if v1.3 is amended:

- §0.1 pins the frozen Phys authority tuple (repo, spec, process, freeze).
- §5–§7 pin `ArtifactRef` as a four-field content-addressed name and give exact byte framing (no raw concatenation, no ambiguity).
- §6.3 pins embedded-ref encoding.
- §7 (primitive encoding) gives canonical encodings for all scalar/collection types and forbids Go maps.
- §8 pins the single MVP referenceable Phys artifact type: `phys/object/1`.
- §9 pins the Expression node set exactly.
- §11 defines `ParameterID` deterministically from `Namespace || ScopePath || DeclarationOrdinal`.
- §12 removes physical-role enums from PhysMath and derives `t`/`k` distinction from parameter identity.
- §13 keeps physical constants outside PhysMath semantics.
- §14 pins the condition model and canonical ordering.
- §15 separates mathematical artifacts from meta-artifacts.
- §16 separates `PhysicalInterpretation`, `PhysicalContract`, and `ProposedInterpretation` with no promotion operation.
- §19–§20 define the formalization protocol and projection classes compositionally with a fixed MVP zero-loss policy.
- §24 pins the `ComputationalContract` schema and the `phys-* → numerical/contract` dependency edge.
- §31 supersession table and §32 No-Invention Matrix are the right closure mechanisms.
- §34 defines a valid blocker and requires a demonstrated counterexample — this is the correct arbitration rule.
- §36 restates the “no layer answers another layer’s question” invariant.
- Appendix A provides concrete schemas for fourteen artifact families.

## II. Demonstrated architectural blockers

Each blocker names the section, the concrete counterexample, and the failure consequence, per §34.2.

### Blocker 1 — Sort count is internally contradictory (16 vs 17)

- §7.1’s mapping table has **16** rows.
- §9’s "core sort families" list has **16** entries.
- §15.1 says `SortID` MUST be one of **17** v1 sort IDs.
- Appendix C’s matrix has **16** rows.

**Concrete counterexample:** A coding agent implementing the closed sort-set validator must decide whether to accept 16 or 17 `SortID` values. Two legitimate implementations exist; the accepted set differs between them.

**Failure consequence:** `MathArtifact` artifacts accepted by one implementation are rejected by the other. Cross-project identity compatibility breaks.

**Exit condition:** state the exact cardinality and enumerate the exact set once, and delete the other mention.

---

### Blocker 2 — `Relation` has two incompatible homes

- §9.2 lists `Relation` as an **Expression node kind**.
- §9.10 defines `Relation` as a **top-level sort** with its own schema.
- §7.1 assigns `relation` a **top-level artifact type**.
- §14.1 says a `MathCondition.Predicate` must resolve to a `Relation` or permitted proposition.

**Concrete counterexample:** A coding agent implementing `physmath.relation` must decide whether a `Relation` is (a) an Expression node whose `ArtifactType` is `expression`; (b) a top-level artifact whose `ArtifactType` is `relation` and which is also embeddable in an Expression; or (c) both, in which case the artifact-type mapping is ambiguous when the same semantic content can appear in either role.

**Failure consequence:** The `ArtifactType` for any Relation differs between implementations; identical semantic content produces different `ArtifactRef`s.

**Exit condition:** declare whether `Relation` is a top-level sort, an Expression node, or both; if both, specify how a top-level Relation artifact and an embedded Relation node differ in identity.

---

### Blocker 3 — Operator and RuleID vocabularies are unpinned

- §10.5 `Operator` has `OperatorID string` — no vocabulary.
- §10.11 `Transformation` has `RuleID string` — no vocabulary.
- §12.1 names only `differentiate` as a canonical operator identity.
- Appendix B names rule-family identifiers (`EXPR-*`, `FN-*`, …) but these are *contract-matrix* families, not `RuleID` values.

**Concrete counterexample:** A coding agent implementing `differentiate`, `simplify`, `substitute`, `limit`, `canonicalize`, or any other MVP operation must invent the closed operation vocabulary. Two implementations may produce compatible-looking but token-incompatible `OperationID`s; transformation traces become non-portable.

**Failure consequence:** `MathTrace` replay fails across implementations; formalization proposals that reference "the operation that produced this expression" cannot resolve.

**Exit condition:** enumerate the closed MVP operator/rule vocabulary with stable identifiers.

---

### Blocker 4 — `ParameterID.Namespace` semantics are undefined

- §11.1 defines `ParameterID = SHA-256(String(Namespace) || Bytes(ScopePathBytes) || UInt32BE(DeclarationOrdinal))`.
- The section does not say what `Namespace` is here.
- §11.4 requires cross-artifact parameter reuse by reference to "its declaration artifact or stable `ParameterID`," but the declaration artifact identity is not pinned.

**Concrete counterexample:** Parameter `t` declared in a `physmath.expression` artifact — is `Namespace` = `physmath`? = the artifact's namespace? = a binder-specific namespace? Two implementations choose different values and produce different `ParameterID`s for the same parameter.

**Failure consequence:** Two artifacts that mathematically share a parameter fail to recognize it; the t/k distinction becomes implementation-dependent.

**Exit condition:** declare the source of the `Namespace` field and the location of the "declaration artifact."

---

### Blocker 5 — `RequestedTarget = "phys.hypothesis_object"` contradicts §8.1

- §8.1: the only referenceable frozen Phys artifact type in MVP is `phys/object/1`.
- §8.2: other Phys structures are not referenceable until a future Phys spec defines an ecosystem contract.
- §19.1: MVP `RequestedTarget = "phys.hypothesis_object"`.

**Concrete counterexample:** A coding agent implementing the formalization target must decide whether `phys.hypothesis_object` is (a) a synonym for `phys/object/1` (in which case the string is redundant and its syntax is misleading); (b) a new Phys artifact type (in which case §8.2 applies and it is not referenceable in MVP); or (c) an ecosystem-level name that maps to `phys/object/1` with additional semantics (unspecified).

**Failure consequence:** FormalizationResponse.ProjectedRefs references either `phys/object/1` or `phys/hypothesis_object/1`, and the two implementations disagree on which.

**Exit condition:** unify the string with §8.1, or define a mapping between them, or remove one of the two.

---

### Blocker 6 — Formalization outcome → hypothesis state mapping is undefined

- §18.4 gives the research state machine.
- §19.3 gives formalization outcomes (`REQUEST_REVISION`, `REJECTED`, `PROJECTABLE`, `PARTIALLY_PROJECTABLE`, `UNREPRESENTABLE`, `PROJECTED_AS_HYPOTHESIS`).
- §18.4 does not specify which outcome triggers which transition from `AWAITING_FORMALIZATION`.

**Concrete counterexample:** When a proposal resolves with `REJECTED`, does the associated `ResearchHypothesis` transition to `REVISION_REQUIRED`, to `CLOSED`, or remain in `AWAITING_FORMALIZATION`? The state machine permits `AWAITING_FORMALIZATION → REVISION_REQUIRED` and `AWAITING_FORMALIZATION → FORMALIZED`, but does not say which outcome corresponds to which. Two implementations choose differently.

**Failure consequence:** Research hypotheses reach inconsistent states across implementations; formalization outcome history becomes non-reproducible.

**Exit condition:** an explicit mapping table from `FormalizationOutcome` to `ResearchState` transition.

---

### Blocker 7 — `MathCondition` artifact status is unclear

- §14.1 gives `MathCondition { Predicate ArtifactRef }`.
- §14.4 requires computing a "condition digest" but does not specify the input to the digest.
- §15.1 defines `MathArtifact { SortID, PayloadBytes }` with `SortID` from the 16/17-sort list. §7.1’s note says `math.condition` is a **meta-artifact type**, not an expression sort.
- Appendix A.2 gives `MathCondition { Predicate ArtifactRef }` without stating its schema version, namespace, or canonical framing.

**Concrete counterexample:** A coding agent implementing condition finalization in §14.4 must compute `condition digest`, but `MathCondition` is neither listed as a `MathArtifact` (with a `SortID`) nor given its own `Namespace`, `ArtifactType`, or `SchemaVersion`. Two implementations may use different framing, producing different condition orderings and dedup results.

**Failure consequence:** Equivalent transformations yield different canonical condition orderings depending on implementation.

**Exit condition:** declare `MathCondition` as either a `MathArtifact` with an assigned `SortID` and `ArtifactType`, or as a non-artifact struct with an explicitly defined digest input.

---

### Blocker 8 — Constant → numerical mapping location is unspecified

- §13.3: "Numerical lowering MAY resolve exact mathematical or physical constants to numerical values only when the owning mathematical/physical contract supplies an explicit deterministic mapping."
- No artifact class is named as "the owning contract" that provides this mapping.
- `PhysicalContract` (§16.4) has no numeric mapping field. `PhysicalInterpretation` (§16.1) has no numeric mapping field. `ComputationalContract` (§24.3) has `NumericParameter {Name, Value}`, but that is instance data, not a symbolic-to-numeric mapping.

**Concrete counterexample:** A numerical lowering tool must convert `math.const.pi` to a `Float64Bits` value. Where does it look up the mapping? In a `PhysicalContract`? In a per-package convention? Two implementations choose different locations and produce non-portable numerical contracts.

**Failure consequence:** `ComputationalContract` cannot be deterministically produced by one implementation and consumed by another.

**Exit condition:** pin the artifact class that owns the constant→numeric mapping and its schema.

## III. Residual issues (not blockers, but ambiguities a coding agent will encounter)

### R-1. Section numbering has a duplicate `§7`

The document contains both `§7 Canonical primitive encoding` and `§7 Namespace registry and ownership`. Subsequent sections (§8 onward) are numbered consistently with the second `§7` being §7 and `§8 Frozen Phys` being §8, so the numbering does not cascade incorrectly — but any reader citing "§7" is ambiguous. This is a citation hazard for a coding agent following acceptance properties.

### R-2. `§19.6` Phys hypothesis API confirmation is a stop-condition

§19.6 correctly says the implementation plan MUST stop if `hypothesis.NewCandidateConcept` is not exposed by the frozen Phys spec. This is a good discipline, but it means v1.3 does not itself confirm the API exists. A coding agent reading v1.3 alone cannot verify whether the formalization protocol has a mint path until it inspects the frozen spec. That is acceptable if §0.1’s authority is unambiguous — but the coding agent must be explicitly told this stop-condition applies at the start of the plan, not discovered mid-implementation.

### R-3. `§9.7` “Rational literal” exponent constraint may over-constrain relative to Phys

§9.7 states the MVP projection rule for `Pow` requires the exponent to be a `Rational` literal. Whether the frozen Phys `Pow` contract permits only rational exponents, or broader exponent forms, is not stated in v1.3. If Phys permits symbolic exponents, v1.3 rejects projections that Phys would accept; that would be a policy choice, not a Phys constraint. The distinction should be stated.

### R-4. `§16.3 ConventionRequirement` namespace ownership

`ConventionRequirement { Namespace, Key, Value }` — the namespace is "the owning framework’s own," but §16.4 does not require any canonicalization against Phys’s convention vocabulary. Two frameworks may declare the same physical convention with different keys; the architecture provides no mechanism to detect equivalence. This is not a blocker (cross-framework convention unification is out of scope), but it should be stated explicitly so the coding agent does not attempt to build it.

### R-5. `§18.5` operation outcomes belong to PhysMath, not TOE-Agent

`MathOperationOutcome` is placed in §18 (“Research artifacts owned by TOE-Agent”). It logically belongs to PhysMath, which produces those outcomes. Minor structural issue.

### R-6. `§23.3` Research meta-ledger is not listed in §18

`ResearchStep` is defined in §23.3 but not listed among the TOE-Agent artifacts in §18 or in Appendix D. It is a durable artifact with an `ArtifactRef` (`OutputRef`), so its ownership, namespace, and schema-version conventions are ambiguous. This is minor but should be unified with §18.

### R-7. `§25.4` mechanics check is scoped to frozen Phys

The check "mechanics has zero object-level assumption keys" is a frozen-Phys invariant, not a `phys-*` conformance rule. Its placement in §25 (“phys-* conformance contract”) mixes Phys invariants with phys-* invariants and may confuse a coding agent about what the package under test is.

### R-8. `§16.5 PhysicalArtifactPayload.PayloadBytes` has no registered schema

The payload schema is package-owned, but no mechanism describes how a consumer (e.g., a numerical lowering tool, or a formalization protocol) can discover or validate the payload schema. This is deliberately left to package contracts, but the mechanism is not described.

## IV. What the document would need to be truly closed

To satisfy the closure condition of §34.5, v1.3 must resolve the eight demonstrated blockers above. Concretely:

1. **Fix the sort count.** Enumerate the exact closed set of `SortID`s once.
2. **Fix `Relation`.** Declare whether it is a top-level sort, an Expression node, or both, and if both, distinguish their `ArtifactRef`s.
3. **Enumerate the MVP operator/rule vocabulary.** Provide closed strings for `OperatorID` and `RuleID`.
4. **Pin `ParameterID.Namespace`.** Define the source of the namespace and where the "declaration artifact" is.
5. **Unify `phys.hypothesis_object` with `phys/object/1`.** One type, one name, one framing.
6. **Add the outcome → state mapping.** A table from `FormalizationOutcome` to a `ResearchState` transition.
7. **Declare `MathCondition`’s artifact status.** Either a `MathArtifact` with `SortID` or a struct with an explicit digest input.
8. **Pin the constant → numeric mapping.** Name the artifact class that owns it and its schema.

Plus the residual issues R-1 through R-8 as clarifications.
