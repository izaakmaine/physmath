# Adversarial Review of `PHYSMATH_PHYS_EXTERNAL_ARCHITECTURE_v1.4.md`

## Executive Verdict
Version 1.4 is a masterpiece of architectural constraint. It successfully resolves the core tensions of the ecosystem: it enforces strict orthogonality between Mathematics and Physics, replaces the dangerous "universal envelope" with explicit reference DAGs, and provides a rigorous, content-addressed identity system. 

However, when subjected to the strict "zero ambiguity for the coding agent" standard, **three critical implementation traps** remain. These are not philosophical flaws; they are exact mechanical ambiguities that will cause a coding agent to either write a buggy canonical encoder, fail to validate a transformation, or silently corrupt a projection.

Below is the adversarial deconstruction of these traps and the exact normative patches required to make v1.4 100% bulletproof for handoff.

## ❌ BLOCKER 1: Go Struct Field Order vs. Canonical Byte Order (The Encoder Trap)
**The Flaw:** 
In §5.1, the `ArtifactRef` Go struct is defined as:
```go
type ArtifactRef struct {
    Namespace     string
    ArtifactType  string   // <--- 2nd field
    SchemaVersion string   // <--- 3rd field
    Digest        [32]byte
}
```
But in §6.2 and §6.3, the normative canonical byte framing explicitly requires:
`Namespace || SchemaVersion || ArtifactType || Digest`
The document even includes a warning: *"The order above is normative even though the Go declaration in §5.1 places `ArtifactType` before `SchemaVersion`."*

**The Implementation Trap:** 
A coding agent will read the Go struct and either (a) use reflection/standard serialization to encode it, resulting in the **wrong byte order** and breaking all artifact identity, or (b) write a custom encoder but accidentally swap the fields because the Go struct order contradicts the wire order. This is a catastrophic determinism failure.

**The Fix:** 
Align the Go struct definition with the canonical wire format. There is no technical reason to keep them mismatched in a specification document.
> **Inject into §5.1:**
> ```go
> type ArtifactRef struct {
>     Namespace     string
>     SchemaVersion string // Reordered to match canonical wire format
>     ArtifactType  string // Reordered to match canonical wire format
>     Digest        [32]byte
> }
> ```
> **Delete the warning in §6.2** about the Go declaration order, as it is no longer applicable.

## ❌ BLOCKER 2: Undefined Semantics for `ID-001` in Transformations
**The Flaw:** 
Appendix B lists `ID-001` as a valid RuleID. Appendix C uses `ID-001` in the `Serialize` column for every mathematical sort. 
However, §10.11 (`Transformation`) requires a `RuleID` string, and states: *"A transformation MUST reject a RuleID that is not listed in Appendix B."* 

**The Implementation Trap:** 
If a coding agent encounters a `Transformation` artifact where `RuleID = "ID-001"`, they will not know what mathematical operation to perform. `ID-001` is defined as the generic serialization rule, but it is not defined as a *mathematical transformation rule*. The agent will either invent a behavior or fail to validate the artifact.

**The Fix:** 
Explicitly define the semantic meaning of `ID-001` when used as a `Transformation.RuleID`, or introduce a dedicated identity rule.
> **Inject into Appendix B (Exact RuleIDs):**
> Add the following definition:
> `ID-001`: "Canonical serialization and identity computation. When used as a `Transformation.RuleID`, it denotes a no-op structural transformation that merely returns the canonicalized output and computes its `ArtifactRef`."

## ❌ BLOCKER 3: Symbol Projection Collision Algorithm is Vague
**The Flaw:** 
Section 33.13 (Acceptance Property: Projection) states:
*"Given source Symbol binding metadata not represented by Phys. When projection runs. Then metadata is ignored as non-semantic strengthening **unless its loss would merge distinct source semantics**."*

**The Implementation Trap:** 
This is a semantic rule, not an algorithm. A coding agent will ask: *"How do I mechanically check if its loss would merge distinct source semantics?"* Without a concrete algorithm, the agent will either always fail projection (too strict) or always ignore `ParameterID` (too loose, causing silent semantic corruption in Phys).

**The Fix:** 
Provide the exact mechanical validation algorithm for Symbol projection.
> **Inject into §20 (Projection contract) or §33.13:**
> **Mechanical Rule for Symbol Projection:** 
> When projecting a `Symbol` to Phys, the system maps the source `DisplayName` to a Phys Symbol. Before accepting the projection, the system MUST verify that no two distinct source `Symbol` nodes in the same expression share the same `DisplayName` but possess different `ParameterID` or `ConstantID` values. 
> If such a collision exists, projection MUST fail with:
> `Classification = UNREPRESENTABLE`
> `ReasonCode = PHYSICAL_SEMANTICS_REQUIRED` (or `SYMBOL_BINDING_COLLISION`).

## ⚠️ MINOR CLARIFICATIONS (To Prevent Agent Hallucination)

### Clarification 1: `TransformResult` is strictly in-memory
The agent might try to create a canonical wire format or an `ArtifactRef` for `TransformResult` (Section 14.2). 
**Rule to add:** "`TransformResult` is an ephemeral, in-memory Go return type for mathematical operations. It is NOT a durable artifact, has no `ArtifactRef`, and has no canonical wire format."

### Clarification 2: `PhysicalContract` is declarative metadata, not executable logic
The agent might try to embed validation rules or code inside the `PhysicalContract` artifact (Section 16.4).
**Rule to add:** "The `PhysicalContract` artifact contains only declarative requirements (e.g., required conditions, required conventions). It does NOT contain executable validation logic. Validation is performed by the owning `phys-*` Go package evaluating the artifact's metadata against its internal code."

### Clarification 3: `Optional` encoding validation for `Symbol`
Section 9.2 encodes `ParameterID` and `ConstantID` as `Optional`. Section 9.3 says "Exactly one... MUST be present in a durable symbolic expression."
**Rule to add:** "While the wire format uses `Optional` to support ephemeral interactive symbols, the validation step for any durable `physmath/expression/1` artifact MUST reject the artifact if a `Symbol` node has both fields set to `0x00` (nil) or both set to `0x01` (present)."
